# Unlimited-OCR — локальный инференс

Локальная версия демо [baidu/Unlimited-OCR](https://huggingface.co/spaces/baidu/Unlimited-OCR):
тот же интерфейс (`index.html` из Space) и тот же стриминг распознанного текста,
но запуск на вашей машине с NVIDIA GPU вместо Hugging Face ZeroGPU.

Модель — `baidu/Unlimited-OCR` (построена на DeepSeek-OCR): «one-shot long-horizon
parsing» — полное распознавание длинных документов и многостраничных PDF за один проход.

> Дальше по проекту: [`docs/ARCHITECTURE.md`](docs/ARCHITECTURE.md) — как это
> устроено внутри, [`ROADMAP.md`](ROADMAP.md) — что запланировано,
> [`CHANGELOG.md`](CHANGELOG.md) — история версий,
> [`CONTRIBUTING.md`](CONTRIBUTING.md) — как контрибьютить.

## Требования

- Linux + NVIDIA GPU, свежий драйвер NVIDIA (сборка torch по умолчанию
  использует CUDA 12.9 — драйвер ≥ 575)
  - **≥ 16 ГБ VRAM** — для bf16-режима (полная точность, единственный
    поддерживаемый GPU-вариант — см. "Возможные проблемы" про AWQ)
  - Без GPU сервер тоже запустится (CPU float32), но очень медленно
- Python 3.12, ~10 ГБ свободного места (torch + веса модели)
- Первый запуск скачает веса модели с Hugging Face (~14 ГБ)

## Установка

```bash
./install.sh
```

Скрипт создаёт `.venv` и ставит зависимости в два шага: сначала
`requirements.txt` (torch, gradio 6 и пр.), затем
`transformers==4.57.1`. Второй шаг нужен потому, что transformers 4.57.1
требует `huggingface-hub<1.0`, а gradio 6 — `>=1.16`; вместе за один
resolve pip их не поставить. После установки pip предупредит о конфликте
с gradio — это ожидаемо, сервер работает (ровно так же это обходится в
самом Space).

## Запуск

```bash
.venv/bin/python app.py
```

Либо — если нужно ещё и подтянуть обновления из GitHub и почистить кеш
Gradio перед запуском:

```bash
./start.sh
```

Откройте **http://127.0.0.1:7860**, в шапке страницы выберите устройство
(**GPU** + точность, сейчас только `bf16`, либо **CPU**) и нажмите
**LOAD** — никакого скрытого автопереключения между вариантами нет, что
выбрали, то и попытается загрузиться. Дождитесь `Model ready: ...` в
интерфейсе/консоли.

- Адрес/порт: переменные окружения `HOST` / `PORT` (по умолчанию `127.0.0.1:7860`);
  при занятом порте сервер сам пробует следующий.
- Принудительный CPU-режим: `UNLIMITED_OCR_DEVICE=cpu .venv/bin/python app.py`.

## Использование

Как в Space:

1. Перетащите картинку или PDF в зону загрузки (PDF отрисуется постранично).
2. Режим — **LONG** или **BASE** (подробнее ниже), Prompt по умолчанию —
   `document parsing.` (можно менять).
3. Устройство — **GPU** (+ точность, сейчас только `bf16`) или **CPU**,
   затем **LOAD**. Дождитесь `Model ready: ...` в интерфейсе/консоли.
4. START — текст появляется потоком, постранично для PDF; COPY — скопировать результат.

### Режимы LONG и BASE — в чём разница

- **LONG** (`gundam`, тайлы 640 px) — изображение режется на тайлы
  пониженного разрешения. Быстрее, лучше подходит для длинных или
  многостраничных документов, где важны скорость и общий охват, а не
  мелкий шрифт в одном конкретном месте.
- **BASE** (1024 px, без нарезки) — вся страница целиком как один "взгляд"
  в более высоком разрешении. Точнее для плотного/мелкого текста на одной
  странице, но медленнее и хуже масштабируется на очень длинные документы.

Если на своих документах разницы не видно — скорее всего, текст не
слишком мелкий/плотный и оба режима справляются одинаково хорошо. Разница
станет заметна на: (а) очень длинных/многостраничных PDF — LONG быстрее;
(б) фото с мелким/плотным текстом — BASE точнее. Рекомендация по
умолчанию: BASE — для важных разовых документов с мелким текстом, LONG —
для быстрой обработки объёмных материалов, где не критична точность до
символа.

## Возможные проблемы

- **CUDA out of memory**: bf16-веса (~6.7 ГБ) не помещаются вместе с
  CUDA-контекстом и активациями на картах с 8 ГБ VRAM. Начиная с 1.3.0
  никакого скрытого автопереключения между вариантами нет — `app.py`
  честно сообщает об ошибке в обоих случаях и ничего не решает за вас:
  - при **загрузке** модели (`LOAD`) — понятная ошибка с предложением
    переключиться на CPU;
  - **во время самого распознавания** (если модель загрузилась, но не
    хватило VRAM на конкретное изображение) — модель автоматически
    выгружается из GPU (`torch.cuda.empty_cache()`), чтобы не держать
    занятую память впустую, но выбор варианта остаётся за вами: сообщение
    прямо просит переключить устройство на **CPU** в шапке страницы и
    нажать **LOAD** заново.

  Bitsandbytes-квантование (8/4-бит) не используется — несовместимо с
  архитектурой модели (MoE + R-SWA). AWQ (`sahilchachra/Unlimited-OCR-AWQ`,
  неофициальная реквантизация) тоже убран из списка вариантов:
  `compressed-tensors` разжимает веса в fp16 прямо перед инференсом, так
  что реального выигрыша по VRAM или скорости в рантайме от него нет
  (экономия только на размере скачивания) — при этом остаётся риск потери
  точности из-за стороннего квантования модели, для которой точность
  распознавания — это весь смысл.

  На картах с 8 ГБ VRAM единственный надёжный вариант — CPU (медленно):
  выберите **CPU** в шапке и нажмите **LOAD**, либо сразу запустите с
  `UNLIMITED_OCR_DEVICE=cpu .venv/bin/python app.py` — в обоих случаях
  процесс сам перезапустится со скрытой CUDA (иначе код модели всё равно
  отправит входные тензоры на GPU, даже если сама модель на CPU).
- **«Expected all tensors to be on the same device»** — модель загрузилась
  на CPU при видимой CUDA из-за старой версии `app.py`: обновитесь
  (`git pull`) и перезапустите.
- **CUDA driver version is insufficient** — драйвер старее CUDA-сборки
  torch. Поставьте свежий драйвер либо нужную сборку torch с
  <https://download.pytorch.org> (например
  `--index-url https://download.pytorch.org/whl/cu126`).
- **pip ругается на huggingface-hub при установке transformers** —
  ожидаемо, см. раздел "Установка" выше.
- Результаты инференса также сохраняются в `.txt`/`.md` во временной
  папке `ocr_out_*` (путь виден в консоли сервера).
