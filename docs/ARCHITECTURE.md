# Архитектура

## Компоненты

```
┌───────────────────────────────────────────────────────────────┐
│                    Frontend (index.html)                       │
│  Прямой порт index.html из HF Space, без изменений:           │
│  PDF.js-превью, терминальный вывод, выбор режима LONG/BASE.   │
└───────────────────────────────────────────────────────────────┘
                            ↓↑ HTTP / SSE
┌───────────────────────────────────────────────────────────────┐
│                     Backend (app.py)                           │
│  Gradio 6 `Server` (обёртка над FastAPI). Эндпоинты:           │
│  GET  /              — отдаёт index.html                       │
│  POST /run_ocr        — стриминг OCR для одной страницы (SSE)  │
│  POST /explode_pdf     — PDF → список PNG-страниц              │
│  POST /load_model      — загрузка/переключение модели (SSE)    │
│  POST /model_status    — что сейчас загружено                  │
└───────────────────────────────────────────────────────────────┘
                            ↓↑ Python API
┌───────────────────────────────────────────────────────────────┐
│            Model layer (transformers + torch)                  │
│  AutoModel.from_pretrained("baidu/Unlimited-OCR", ...)         │
│  model.infer(tokenizer, prompt=..., image_file=..., ...)       │
└───────────────────────────────────────────────────────────────┘
```

## Поток данных

1. **Загрузка модели** (`/load_model`)
   - Пользователь выбирает вариант в шапке UI явно: устройство **GPU**
     (+ точность, сейчас только `bf16`) или **CPU**. Никакого `auto` и
     никакой скрытой цепочки фолбэков больше нет (убрано в 1.3.0) — что
     выбрали, то и пытается загрузиться.
   - `_load_model_sync()` выполняется в отдельном потоке, кладёт прогресс
     в `queue.Queue`; генератор `load_model()` читает очередь и стримит
     прогресс клиенту через SSE (`stream_every=0.5`).
   - При CUDA OOM на этапе загрузки — `_load_model_sync()` явно выгружает
     модель (`model = None`, `empty_cache`) и поднимает `RuntimeError` с
     понятным текстом ("переключите на CPU и нажмите LOAD"). Никакого
     автоматического перехода на другой вариант — раньше (до 1.3.0)
     `auto` тихо пробовал следующий вариант в цепочке, что на практике
     не решало реальную проблему (см. ниже) и маскировало факт, что
     VRAM не хватает.
   - AWQ (`sahilchachra/Unlimited-OCR-AWQ`) был в списке вариантов до
     1.2.3 и убран: `compressed-tensors` разжимает веса в fp16 прямо
     перед инференсом, поэтому реального выигрыша по VRAM/скорости в
     рантайме нет (только меньше объём скачивания), а риск потери
     точности от стороннего квантования остаётся. Чистый минус без
     плюсов — см. `CHANGELOG.md`.
   - Для CPU-режима: если CUDA видна процессу, `model.infer()` из кода
     модели всё равно шлёт тензоры на `cuda` — поэтому сервер сам
     перезапускается через `os.execve()` с `CUDA_VISIBLE_DEVICES=""`
     (см. `cpu_restart` в `_load_model_sync`/`load_model`). Фронтенд
     детектирует стадию `"Restarting server..."`, поллит `/` до первого
     успешного ответа и сам делает `location.reload()` с `?device=cpu` в
     URL, чтобы после перезагрузки страницы устройство осталось
     выбранным как CPU (см. `_waitForServerAndReload()` в `index.html`).

2. **Обработка изображения/PDF**
   - PDF: `/explode_pdf` конвертирует каждую страницу в PNG через
     PyMuPDF (`fitz`, DPI=300 по умолчанию — поднят с 200 в 1.3.0 для
     лучшего распознавания мелкого текста) во временную папку `pdf_ocr_*`.
   - Для каждой картинки (или для одиночного изображения) фронтенд
     вызывает `/run_ocr`, передавая также `ngram_guard` (состояние
     тумблера NGRAM в шапке — с 1.3.0 реально влияет на
     `no_repeat_ngram_size`, раньше это был "мёртвый", ни к чему не
     подключённый переключатель).
   - `run_ocr()` запускает `model.infer(...)` в отдельном потоке.
     Модель печатает токены в `stdout` — `ThreadTargetedStdout` перехватывает
     именно вывод *этого* потока (по `threading.current_thread()`), кладёт
     его в очередь, генератор стримит накопленный текст клиенту
     (`stream_every=0.1`). TPS-строки ("tps:", "tokens/s") отфильтровываются.
   - **CUDA OOM во время самого инференса** (модель загружена, но не
     хватило VRAM на конкретное изображение — активации/KV-cache) — это
     отдельный путь ошибки от OOM при загрузке (см. п.1), и до 1.3.0 он
     вообще не обрабатывался: модель оставалась висеть на GPU, VRAM не
     освобождалась, никакого уведомления не было. С 1.3.0
     `_infer_thread` ловит CUDA OOM отдельно, `run_ocr()` явно выгружает
     модель (`model = None`, `torch.cuda.empty_cache()`, `gc.collect()`)
     и поднимает понятную ошибку с просьбой переключиться на CPU — без
     скрытого автопереключения.
   - После завершения инференса `_collect_output()` читает финальный
     `.txt`/`.md` из `output_path`, отданного модели (`save_results=True`).
     Если этот чистый текст совпадает с тем, что уже было показано вживую
     через stdout-перехват — просто отдаётся как есть (без повторного
     "мигания" одинаковым текстом). Если отличается (например, live-текст
     из stdout был неполным/грязным) — реально проигрывается клиенту
     посимвольно с небольшой задержкой (эффект печатающей машинки, как в
     референсном Space), но ограничено по общему времени (~200 шагов,
     ~2.4 сек максимум) — на длинных документах шаг увеличивается, чтобы
     не растягивать анимацию до бесконечности.

3. **Стриминг** — любой генератор, обёрнутый `@app.api()`, автоматически
   стримится клиенту через SSE. Формат сообщений:
   - `run_ocr`: `{"text": str, "done": bool}`
   - `load_model`: `{"stage": str, "ready": bool, "label": str | None}`

## Синхронизация / блокировки

| Блокировка | Что защищает | Кто берёт |
|---|---|---|
| `_model_state_lock` | глобальные `model`, `tokenizer`, `_model_label` | `_load_model_sync`, `run_ocr`, `model_status`, `_cleanup` |
| `_infer_lock` | «один инференс *или* одна загрузка модели за раз» | `load_model` (неблокирующий `acquire`, чтобы не грузить модель поверх идущего инференса) и `run_ocr` (тоже неблокирующий `acquire`, держит лок **на весь запрос**, а не только внутри `model.infer()`) |
| `_temp_dirs_lock` | список временных папок для очистки при выходе | везде, где создаётся temp-папка, и в `_cleanup()` |

Важно: `_infer_lock` держится `run_ocr()` с момента входа в функцию (после
проверки, что модель загружена) **до момента, когда поток инференса
реально завершён и результат уже прочитан из файла** (`_collect_output`) —
это отдельно от **старой** схемы, где лок брался только внутри рабочего
потока вокруг `model.infer()`. Так параллельный `load_model()` не может
выгрузить или подменить модель, пока идёт инференс — оба пути используют
один и тот же лок и оба берут его неблокирующим `acquire(blocking=False)`,
отвечая пользователю понятным сообщением вместо тихого зависания.

Лок освобождается явным `_infer_lock.release()` **до** последнего блока
`run_ocr()`, который просто повторно стримит клиенту уже готовый текст
посимвольно (для UI) — эта часть не трогает модель/GPU и лока не требует.
Это сделано намеренно: release нельзя откладывать до конца тела
генератора, полагаясь на то, что SSE-обёртка вызовет `next()` ещё раз
после payload'а с `"done": true` — если обёртка перестаёт опрашивать
генератор, как только видит `done: true` (разумная оптимизация с её
стороны), тело функции так и останется подвешенным на последнем `yield`,
и `finally` с `_infer_lock.release()` в конце функции никогда не
выполнится — лок «утечёт» до перезапуска процесса. Именно так проявлялся
баг «Another OCR run or model load is in progress» после уже успешно
завершённого запроса (исправлено в 1.2.2).

## Модуль `app.py`: карта функций

| Функция | Назначение |
|---|---|
| `_cleanup()` | освобождает модель/токенизатор, чистит временные папки при выходе (`atexit`) |
| `_variant_kwargs(name)` | kwargs для `from_pretrained` + целевое устройство по названию варианта |
| `_load_model_sync(variant, q)` | синхронная загрузка ровно запрошенного варианта с прогрессом в очередь; при ошибке (в т.ч. OOM) поднимает `RuntimeError` с понятным текстом, без автопереключения на другой вариант |
| `_target_label(variant)` | какой лейбл будет пытаться загрузить данный `variant` (для проверки "уже загружено") |
| `load_model(variant)` | `@app.api()` — стримит прогресс загрузки, координирует CPU-рестарт. `variant` — `"bf16"` или `"cpu"`, без `"auto"` (убран в 1.3.0) |
| `model_status()` | `@app.api()` — что сейчас загружено |
| `pdf_to_images(pdf_path, dpi=300)` | PDF → список путей к PNG-страницам |
| `_collect_output(out_dir)` | финальное чтение `.txt`/`.md`, написанных `model.infer()` |
| `ThreadTargetedStdout` | патч `sys.stdout`, изолирующий вывод конкретного потока инференса |
| `run_ocr(image_path, mode, prompt, ngram_guard)` | `@app.api()` — основной OCR-эндпоинт со стримингом; ловит CUDA OOM в потоке инференса отдельно и выгружает модель |
| `explode_pdf(pdf_file)` | `@app.api()` — PDF → PNG постранично (DPI=300) |
| `homepage()` | отдаёт `index.html` |

## Известные ограничения архитектуры

- **Один пользователь одновременно.** `_infer_lock` сериализует всё —
  это осознанное упрощение для локального однопользовательского
  инструмента, не для многопользовательского сервиса. Если понадобится
  многопользовательский режим — нужна очередь задач (Celery/RQ) и
  что-то вроде пула воркеров с отдельными GPU-контекстами, а не просто
  снятие лока.
- **Никакого автопереключения между вариантами модели (с 1.3.0).**
  Раньше `auto` тихо пробовал GPU, потом CPU. Это убрано намеренно —
  подобная "магия" маскировала реальные проблемы (например, OOM
  случался не на загрузке, а посреди инференса — цепочка фолбэков на
  загрузке от этого вообще не спасала, см. `CHANGELOG.md` 1.3.0) и
  путала пользователя, почему в итоге загрузился не тот вариант, что он
  выбрал. Если понадобится вернуть что-то похожее на "умный" выбор —
  делайте это заметным для пользователя действием, а не тихим свопом.
- **CPU-рестарт полностью сбрасывает процесс.** `os.execve()` — новый
  процесс не помнит, что до рестарта пользователь хотел CPU-вариант;
  ждёт нажатия LOAD заново. Фронтенд помогает восстановить *выбор
  устройства* через `?device=cpu` в URL при перезагрузке страницы, но
  саму загрузку модели пользователь всё равно инициирует сам.
- **Bitsandbytes-квантование не используется.** Комментарии в коде и
  практический опыт показывают несовместимость с MoE + R-SWA
  архитектурой модели. Если это перепроверяется в будущем — обновите
  и этот файл, и `README.md`/`install.sh`.
- **`stdout`-перехват завязан на конкретный формат вывода модели**
  (`"tps:"`, `"tokens/s"` как маркеры служебных строк). Если апстрим
  изменит формат логов модели — фильтрация в `ThreadTargetedStdout`
  перестанет работать корректно, стоит перепроверить при обновлении
  версии `transformers`/весов модели.
